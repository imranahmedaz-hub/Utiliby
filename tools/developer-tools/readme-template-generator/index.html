What makes a good README?

A README is the front page of your project. It is the first thing a visitor sees on GitHub, and the last thing they read before deciding whether to install, star or contribute. A good README answers five questions in the first ten seconds: What does this do? Who is it for? How do I install it? How do I use it? What is the license?

The structure below is the one used by the most popular open-source projects, and it is what this generator produces by default:

Not every project needs every section. A small utility library may only need title, install and usage. A large application benefits from the full set.

How badges work in a README

Badges are small SVG images served by shields.io and embedded in Markdown with the standard image syntax:

[![License: MIT](https://img.shields.io/badge/License-MIT-blue.svg)](https://opensource.org/licenses/MIT)

The outer [...] makes the image clickable and links to the license page. The inner ![alt](url) is the standard Markdown image. Shields.io generates the SVG dynamically from the URL, so the badge always shows the current value — a build-status badge updates automatically when the build passes or fails.

Project README vs profile README

There are two distinct kinds of README on GitHub, and they serve different purposes.

A project README lives in a repository and documents that repository. It answers "what is this project, how do I install it, how do I use it". This is the default template in the generator.

A profile README lives in a special repository named after your GitHub username (username/username). It appears at the top of your GitHub profile page, above your pinned repositories. Instead of documenting a project, it introduces you as a developer: your name, what you build, your tech stack, how to reach you, and any fun statistics (GitHub stats cards, streak counters, top languages). The Profile template in this generator produces that structure.

Profile READMEs often use dynamic SVG cards from services like github-readme-stats, github-readme-streak-stats and github-profile-trophy. These are embedded as standard Markdown images with query parameters for theme, colours and layout.

GitHub-flavored Markdown essentials

GitHub uses a superset of standard Markdown called GitHub-flavored Markdown (GFM). The features that matter most for READMEs are:

  • Tables — pipe-delimited, with an optional alignment row. Used for feature comparisons, configuration options and badge lists.
  • Task lists — - [ ] for unchecked, - [x] for checked. GitHub renders these as interactive checkboxes, useful for roadmaps and contributing checklists.
  • Fenced code blocks — triple backticks with an optional language identifier for syntax highlighting: ```javascript.
  • Collapsible sections — using the <details> and <summary> HTML tags. Useful for long FAQ sections that would otherwise dominate the README.
  • Alerts — GitHub-specific blockquote syntax: > [!NOTE], > [!TIP], > [!WARNING], > [!IMPORTANT]. These render as coloured callout boxes on GitHub but may not render on GitLab or Bitbucket.
  • Mermaid diagrams — fenced code blocks with the mermaid language identifier render as flowcharts, sequence diagrams and Gantt charts on GitHub.
  • Relative links — link to other files in the same repository with a relative path: [Contributing](CONTRIBUTING.md).
  • Anchors — link to a section within the README using the heading text, lowercased and hyphenated: [Installation](#installation).

README SEO and GitHub discoverability

A README is also an SEO asset. GitHub pages rank in Google search, and a well-structured README can drive organic traffic to your project. To optimise:

  • Put the keywords in the H1 and the first paragraph. If your project is a "fast CSV parser for Node.js", say exactly that in the first line.
  • Use descriptive alt text on images and badges. ![Build passing](...) is better than ![](...).
  • Include the project name in the repository description and topics. The README cannot change these, but they appear alongside it in search results.
  • Write natural prose, not keyword soup. Google's ranking systems are increasingly good at detecting stuffed text.
  • Link to related projects and documentation. Internal links to /docs and external links to relevant resources improve the page's authority.
  • Keep the README up to date. Stale installation instructions and broken links hurt both user trust and search ranking.

Common README mistakes

  • No installation instructions. The most common gap. Every project that can be installed should show the exact command.
  • No usage example. Features list is not the same as usage. Show a minimal working example.
  • Broken or missing badges. A badge that shows "unknown" or a broken image looks worse than no badge at all.
  • Badges that do not update. A hard-coded "build passing" badge is misleading. Use the shields.io dynamic URL for build status.
  • Too long without a table of contents. Anything over 1,000 words should have a TOC.
  • No license. A project without a license is legally "all rights reserved", which discourages use and contribution.
  • Walls of text. Use headings, bullet lists, code blocks and tables to break up content.
  • Outdated screenshots. If the UI has changed, remove or update the screenshot.
  • No contributing section. Contributors want to know how to submit a PR, what the code style is, and how to run tests.

Frequently asked questions

What is a free README template generator online?

A free README template generator online builds a complete README.md from a form. You enter your project details and the tool outputs valid GitHub-flavored Markdown with optional badges, a table of contents and section headings, plus a live GitHub-style preview and a download button.

What sections should a good README have?

A well-structured README includes: project title, one-line description, badges (build, version, license), a short introduction, a table of contents for longer files, installation instructions, usage examples, features list, configuration, contributing guidelines, license and acknowledgments. Not every project needs every section.

How do I add badges to my README?

Badges are SVG images served by shields.io and embedded with standard Markdown image syntax: [![alt text](badge-url)](link-url). This tool includes a badge builder that generates the correct URLs for license, build status, version, stars, forks, downloads and more.

What is the difference between a project README and a profile README?

A project README documents a single repository. A profile README lives in a repository named after your username (username/username) and appears on your GitHub profile page. It introduces you as a developer rather than a project.

What is GitHub-flavored Markdown?

GitHub-flavored Markdown (GFM) is a superset of standard Markdown that adds tables, task lists, strikethrough, autolinks, fenced code blocks with syntax highlighting, and several other extensions. GitHub, GitLab and Bitbucket all support GFM.

How long should a README be?

Long enough to answer the reader's questions, short enough to be scannable. A typical README is 200 to 800 words. Large projects may run to 1,500 words with a table of contents. If it exceeds 2,000 words, consider moving detail to a /docs folder.
